# Known limitations and honest scope

1. **No live LLM integration.** The baseline uses deterministic rules and zero model calls. This avoids unsupported claims, API-key requirements, external retention, and non-reproducible outputs. Model faults are recorded and handled by the safe deterministic path; the project does not invoke a hosted provider.
2. **No live push/WhatsApp provider.** The agent now emits policy-verified push and WhatsApp actions for the supplied simulator, including approved template variables and deferred quiet-hour sends. It does not call Firebase, WhatsApp Business API, or any external provider, so simulator delivery is not proof of real-world delivery.
3. **Single-process replay.** Viewer state is written as JSON files. This is appropriate for a reproducible take-home but not a production concurrency guarantee. Production would need transactional state, an outbox, a durable queue, locking/idempotency constraints, backpressure, and observability.
4. **Latency scope.** Reported latency is local computation time. It does not include network transit, queueing, provider latency, or a production publishing backend.
5. **Goal semantics.** The supplied rules include ambiguity. G10 is not selected because it has no event success signal. G07 requires an episode-history interpretation; G08 restricts success to recently released catalogue titles; G09 requires play events on three distinct IST calendar days. These interpretations are encoded and should be revisited with the product owner.
6. **Outcome simulator coverage.** Simulator output is synthetic and covers triggered users. It is useful for exercising action validation and goal logic but is not causal evidence. The causal report uses the historical randomized treatment/holdout assignment.
7. **Statistical uncertainty.** The historical pilot report uses a simple 95% Wald interval for the difference in proportions. A production-grade analysis should use a more robust interval or randomization-based inference and pre-register the primary endpoint.
8. **Event clock assumptions.** Staleness uses `received_at - occurred_at` with a ten-minute threshold, consistent with the supplied replay convention. If the source clock is known to be wrong, production should use an explicit clock-skew model and source-specific freshness policy.
9. **No live data mutation.** Control events are applied during the replay, and withdrawn titles are filtered at action time. This is an offline replay rather than a service that consumes streaming control events continuously.
10. **Not production-certified.** The repository is a take-home baseline. The candidate should run the commands, review generated outputs, and be able to explain the design and trade-offs in the technical discussion.
